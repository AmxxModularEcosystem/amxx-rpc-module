# 08. Открытые вопросы, допущения и принятые решения

## 1. Принятые решения

| # | Решение | Обоснование |
|---|---|---|
| AD-1 | **Модуль — чистый транспорт.** Семантика MCP (tools/list, tools/call) и каталог tools живут в `amxb`, вне этого репозитория. | Владелец: не смешивать MCP в модуль; менять tool-surface без пересборки C++. Было развилкой 1. |
| AD-2 | **Встроенное ядро методов + нативы регистрации** методов Pawn-плагинами. | Нужны готовые команды/состояние и расширяемость для доменов (напр. ExtendedStats). Развилка 2. |
| AD-3 | **Фейк-игроки: гибрид** — собственный usercmd-слой (движение/прицел/стрельба/состояние) + **опциональный YAPB** только для навигации/«подойти». zBot **не** используется как программный контроль (нет стабильного API). | zBot: только Orpheu/server-cmd (хрупко); YAPB: стабильный `IBotModule`, но без attack; выстрел — своим usercmd-слоем. Развилка 3. |
| AD-4 | **Сборка — CMake** (Windows MSVC Win32, Linux `-m32`). | Привычнее вне экосистемы, обильный prior art, свой CI. Развилка 4. |
| AD-5 | **Транспорт: TCP `127.0.0.1` + обязательный токен** в конфиге. | Просто и безопасно; loopback по умолчанию. Развилка 5. |
| AD-6 | **Имя продукта — AmxxRpc**; репозиторий `amxx-rpc`; модуль `amxxrpc_amxx`; нативы `ARpc_*`; инклюд `AmxxRpc/Core.inc`. | MCP в имени лишний (MCP — в amxb). |

| AD-17 | **Доступ команд:** `amxxrpc_reload/status/clients` — `ADMIN_RCON`; `help` — без ограничений. | OQ-8 закрыт (`design/16` §4). |
| AD-18 | **Конфиг — плоский `key=value`**; reload с pre-bind; live/restart-области. | OQ-1 закрыт (`design/16` §1/§3). |
| AD-19 | **Диспетч Pawn — per-method SP-forward.** | OQ-2 закрыт (`design/12` §4). |
| AD-20 | **`requestId` — монотонный `uint32`**, async-ответ, таймаут, без generation/slot. | OQ-3 закрыт (`design/12` §3). |

## 2. Допущения

- **AS-1.** Целевой сервер — ReHLDS + Metamod + AMXX 1.10.5428 (подтверждено на тест-сервере).
- **AS-2.** Тест-сервер 32-битный; сборка нацелена на `_amxx_i386.so`/`_amxx.dll`.
- **AS-3.** Внешний MCP-мост в `amxb` умеет общаться с модулем по TCP (это вне нашего репо).

## 4. Риски

- **R-1.** Гонки/краши при обращении к AMXX из неглавного потока — митигация: жёсткая
  двухпоточная модель (`AR-001…006`) и запрет на AMXX в I/O-потоке.
- **R-2.** Хрупкость движковых хуков при смене версии ReHLDS/Metamod — митигация: узкая
  поверхность хуков, деградация без падения.
- **R-3.** ABI YAPB (`GetBotAPI`) зависит от компилятора/STL — митигация: опциональность,
  отсутствие жёсткой зависимости.
- **R-4.** Токен/loopback обходятся при явной смене bind — митигация: документация, дефолт loopback.
- **R-5.** `server.exec`/`cvar.set` = RCE на сервере для владельца токена — доверенная граница,
  документируется; cleartext при не-loopback bind (`design/10` §7.9).
- **R-6.** `fake.*` может исчерпать клиент-слоты и вытеснить реальных игроков — митигация:
  `fake_max`, отказ на реальных игроков (`FR-FAKE-009`).
- **R-7.** Плагин может попытаться переопределить core-метод — митигация: запрет в реестре
  (`design/10` §7.10).
- **R-8.** Deep/large JSON как DoS — митигация: лимит размера + depth-guard (OQ-15).
- **R-9.** `join` зависает при `select`/блокирующей записи — митигация: wakeup-канал +
  неблокирующий I/O (`design/10` §4).
- **R-10.** `dlopen` YAPB как библиотеки без регистрации плагином может дать `GetBotAPI == NULL`
  — митигация: детект уже загруженного YAPB, деградация (OQ-7).
- **R-11.** Логирование из I/O-потока через AMXX-API — запрещено; нужен потокобезопасный
  сток (файл/очередь в main) (`AR-002`).
