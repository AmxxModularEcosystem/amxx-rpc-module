# 02. Транспорт и протокол

## 1. Транспорт

- **TCP**, адрес по умолчанию `127.0.0.1`, порт из конфига (дефолт `27016`).
- Несколько одновременных соединений (лимит в конфиге). Каждое соединение — сессия
  с собственной подпиской и (опц.) контекстом.
- Сокет в **неблокирующем** режиме; I/O-поток обслуживает `accept`/`recv`/`send`
  (см. `design/10` §«Потоки»). Главный поток сокет не трогает.
- Windows: Winsock (`WSAStartup`/`WSACleanup`, `ws2_32`/`wsock32`); Linux: BSD-сокеты.
  Кросс-платформенная обёртка — по образцу AMXX `modules/sockets`.

## 2. Фрейминг

- **Одно JSON-сообщение на строку**, разделитель `\n` (LF). Сообщение не содержит
  встроенных переводов строк. UTF-8.
- Частичный приём буферизуется до появления `\n`; соблюдаются `FR-TRANSPORT-004`.
- Максимальный размер сообщения — `max_message_bytes` (конфиг). Превышение → ошибка
  и закрытие соединения.
- Idle-таймаут — `idle_timeout` (конфиг).

## 3. Аутентификация

- После установления соединения клиент **обязан** первым сообщением вызвать
  `rpc.auth` с токеном:
  ```json
  {"jsonrpc":"2.0","id":1,"method":"rpc.auth","params":{"token":"<secret>"}}
  ```
- Успех → `{"jsonrpc":"2.0","id":1,"result":{"ok":true}}`; любое иное сообщение до
  аутентификации или неверный токен → ответ об ошибке и **закрытие** соединения.
- Токен не логируется и не отражается в ответах (`AR-009`).

## 4. JSON-RPC 2.0

- Поддерживаются `request` (с `id`), `response`, `notification` (без `id`).
- Методы — строки `<область>.<действие>` (`rpc.*`, `server.*`, `cvar.*`, `players.*`,
  `logs.*`, `fake.*`, `bot.*`, а также зарегистрированные плагинами).
- **Коды ошибок** (стандарт + прикладные):

| Код | Значение |
|---|---|
| `-32700` | Parse error (невалидный JSON) |
| `-32600` | Invalid Request |
| `-32601` | Method not found |
| `-32602` | Invalid params |
| `-32603` | Internal error |
| `-32001` | Not authenticated (терминальная: далее close) |
| `-32002` | Service unavailable (напр. YAPB отсутствует) |
| `-32003` | Engine/AMXX error (ошибка исполнения метода) |
| `-32004` | Server busy (переполнение очереди запросов) |
| `-32005` | Request timeout (неответивший запрос; late-reply отбрасывается) |

## 5. Нотификации сервер → клиент

- Push-нотификации для подписок: `{"jsonrpc":"2.0","method":"<event>","params":{...}}`.
- События формируются на главном потоке, кладутся в очередь `main → I/O`, отправляются
  I/O-потоком.
- Подсчёт ссылок/идентификатор подписки — чтобы отписаться и не слать лишнее.
- **Порядок:** ответы одного клиента сохраняют FIFO-порядок отправки; разные запросы могут
  отвечать не по порядку (JSON-RPC допускает сопоставление по `id`). Нотификации дропаются
  первыми при переполнении очереди `main→I/O` (ответы — никогда).

## 5а. Дополнения по ревью

- **Pre-auth timeout:** соединение, не отправившее `rpc.auth` за `idle_timeout`, закрывается
  (отдельного «висящего» состояния нет).
- **Частичная запись:** неблокирующий `send` с `EWOULDBLOCK` буферизуется на соединении и
  досылается при готовности к записи (см. `design/10` §4).
- **Лимит сообщения** проверяется по мере накопления байт, не после `\n`.

## 6. Ограничения и защита

- Ограничение числа соединений, размера сообщения, idle-таймаута.
- При переполнении очередей — отказ с понятной ошибкой, без неограниченного роста памяти.
- Loopback по умолчанию (`AR-007`); удалённый bind — осознанное действие владельца.

## 7. Открытые детали (в дизайн-док)

- Точный формат `rpc.auth` (токен в первом сообщении против заголовка-префикса).
- Поддержка батчей JSON-RPC (массив) — решить в `design/10`.
- Хранение нескольких клиентских сессий и лимит на клиента.
