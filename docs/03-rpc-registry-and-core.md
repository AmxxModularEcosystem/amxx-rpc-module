# 03. Реестр методов, ядро и Pawn-API

> **Ревизия (Этап 2, `design/12`):** `logs.tail` и раундовые/килл-события **отложены** (v1 —
> connect/disconnect/map); `server.exec` → `{ok:true}` (захват вывода отложен, `FR-RPC-008`);
> диспетч Pawn — **per-method SP-forward**; нативы **модуля** регистрируются через `MF_AddNatives`
> (не Pawn `register_native`; `@ARpc_*` — обработчики плагина); `requestId` — монотонный `uint32`.
> Актуальные контракты — в `design/12`.

## 1. Реестр методов

- Реестр — упорядоченная таблица `имя → { source: builtin | pawn, handler, meta }`.
- Имена — `<область>.<действие>` (`rpc.ping`, `server.exec`, `fake.create`, …).
- Коллизии: повторная регистрация имени Pawn-плагином — **ошибка**; **core-методы
  (`rpc.*`, `server.exec`, `cvar.*`) плагину переопределять запрещено** (защита, `design/10`
  §7.10). Резолв — в `design/12`.
- `rpc.methods` возвращает каталог (имя, источник, краткое описание).

## 2. Диспетчеризация (потокобезопасность)

- Приём и парсинг — I/O-поток; запрос кладётся в очередь `I/O → main`.
- Диспетчер (`Rpc_*`) вызывается **на главном потоке** (StartFrame):
  1. найти метод в реестре;
  2. builtin → вызвать C++-обработчик (движок/AMXX — допустимо, мы в главном потоке);
  3. pawn → вызвать публичный колбэк плагина-владельца;
  4. сформировать ответ и положить в очередь `main → I/O`.
- Асинхронный ответ разрешён: Pawn-обработчик может ответить позже (например, через
  `set_task`), но **только с главного потока**. Неответившие запросы истекают по таймауту.

## 3. JSON в модуле

- Модуль нуждается в собственном JSON-парсере/сериализаторе (AMXX `json`-модуль
  недоступен из C++). Кандидат — **`parson`** (MIT; используется в `third_party` AMXX).
- Для Pawn параметры/результаты передаются **JSON-строками**; плагин парсит их
  доступными средствами (модуль `json`).

## 4. Pawn-API (нативы регистрации и ответа)

Публичный инклюд — `AmxxRpc/Core.inc`. Стиль — дефолтная регистрация (`ARpc_*`, `@ARpc_*`).

```pawn
// Регистрация метода; callback — публичная функция плагина
native ARpc_Core_RegisterMethod(const name[], const callback[], const description[] = "");
native ARpc_Core_UnregisterMethod(const name[]);

// Ответ на запрос (requestId приходит в callback)
native ARpc_Core_Reply(const requestId, const resultJson[]);
native ARpc_Core_ReplyError(const requestId, const errorCode, const message[]);

// Событие от плагина → внешним подписчикам (push-нотификация)
native ARpc_Core_Emit(const event[], const payloadJson[]);

// Сервисные
native ARpc_Core_IsConnected();          // есть ли аутентифицированные клиенты
native ARpc_Core_GetVersion(out[], len);
```

Обработчик регистрируется как публичная функция:

```pawn
public MyMethod_Handler(const requestId, const paramsJson[])
{
    // ... разобрать paramsJson, выполнить действие
    ARpc_Core_Reply(requestId, "{\"ok\":true}");
}
```

Константы ошибок — `ARP_ERR_*` (дублируют прикладные коды `-32001…-32003`, `02` §4).

## 5. Встроенное ядро методов

Минимальный набор (расширяется по этапам):

| Метод | Назначение |
|---|---|
| `rpc.auth` | токен-аутентификация сессии (`02` §3). **Транспортный уровень, обрабатывается на I/O-потоке, не в реестре.** |
| `rpc.ping` | живость |
| `rpc.version` | версия модуля/протокола |
| `rpc.methods` | каталог зарегистрированных методов |
| `server.exec` | исполнить серверную команду |
| `cvar.get` / `cvar.set` | чтение/запись cvar |
| `players.list` / `players.get` | состояние игроков |
| `events.subscribe` / `events.unsubscribe` | подписки |
| `logs.tail` | хвост лога (опц.) |

Методы фейк-игроков (`fake.*`) — подсистема `Fake_*` (`04`); боты (`bot.*`) — адаптер (`04` §4).

## 5а. Захват вывода `server.exec` (требует решения в `design/11`)

- `pfnServerCommand`/`pfnServerExecute` **не возвращают** вывод команды. Варианты:
  (а) вернуть только `{ok:true}` (команда исполнена, без вывода);
  (б) перехватить консольный вывод хуком (`SV_Printf`/`Con_Printf`-эквивалент через
  ReHLDS-хукчейн) с буферизацией за окно исполнения.
- До реализации зафиксировать выбранный вариант и его ограничения (асинхронность консольного
  вывода). `FR-RPC-008`.

## 5б. Прочие детали по ревью

- `ARpc_Core_Reply(resultJson)` — модуль **валидирует** JSON перед вставкой в ответ; невалидный
  → `-32603`, запрос считается завершённым ошибкой.
- Notifications (без `id`) в Pawn-обработчик приходят с sentinel-`requestId`; `Reply` по ним
  игнорируется (только `Emit`).
- Управление подписками/лимитами и метаданные метода (схема параметров) — в `design/12`.

## 6. События (push)

- Источники: движковые/AMXX события (round start/end, kill, connect/disconnect, spawn)
  и события, эмитированные плагинами (`ARpc_Core_Emit`).
- Формируются на главном потоке, отправляются подписчикам через очередь `main → I/O`.
- Подписка — на именованные события; фильтры (если нужны) — в дизайне.

## 7. Открытые детали (в дизайн-док)

- Единый forward vs per-method SP-forward для Pawn-обработчиков.
- Формат возврата `requestId` (opaque int/handle) и его срок жизни.
- Батчи и порядок ответов; поведение при частичном отказе.
- Каталог метаданных метода (схема параметров) для MCP-моста.
