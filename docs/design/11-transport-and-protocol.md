# 11. Транспорт и протокол (дизайн)

Статус: **черновик (на согласование)**. Область: TCP-сервер, фрейминг, JSON-RPC 2.0,
аутентификация, очереди и обмен I/O↔main, жизненный цикл запроса, shutdown. Требования —
`docs/02`, `docs/01` (AR-001…010, FR-TRANSPORT-*, FR-CONF-*), `docs/design/10` §4.

## 1. Компоненты

| Файл | Ответственность |
|---|---|
| `Config.h/.cpp` | чтение/reload конфига, fail-fast |
| `Queue.h` | шаблон мьютекс-очереди + condition variable |
| `Protocol.h/.cpp` | JSON-RPC кодек (парсинг/сборка), коды ошибок, depth/размер guard |
| `Transport.h/.cpp` | listen/accept, соединения, буферы, фрейминг, auth, I/O-поток |
| `RpcDispatch.h/.cpp` | дренаж очереди `I/O→main` в `StartFrame` (в Этапе 1 — мин. набор методов) |
| `Log.h/.cpp` | потокобезопасный лог (файл/очередь в main; не AMXX из I/O) |

## 2. JSON

- Библиотека — **`parson`** (MIT, C; вендорится в `third_party/parson/`). Реентрантна.
- **Guard:** лимит глубины (напр. 32) и размера; превышение → `-32700`/`-32600` + close.
- Числовой `id` может быть большим — хранить исходный `id` как строку/`double` без потери;
  для Pawn внутренний handle — целое (см. §6).

## 3. Транспорт (резолв из `design/10` §4)

- Один I/O-поток, **неблокирующий мультисокет**: `select` (Linux + Windows; `WSAPoll` опц.).
  `FD_SETSIZE` учитывается; при лимите ≤ 64 — ок.
- listen на `host:port`; `SO_REUSEADDR`; `TCP_NODELAY`; bind default `127.0.0.1`.
- `accept` в цикле до `EWOULDBLOCK`; enforce `max_connections` (иначе отказ+close).
- На соединение: входной буфер (накопление до `\n`, лимит `max_message_bytes` **по мере
  накопления**), выходной буфер (частичная запись при `EWOULDBLOCK`, регистрация на writability).
- Idle `idle_timeout`; pre-auth соединение без `rpc.auth` закрывается тем же таймаутом.

## 4. Фрейминг

- Одно JSON-сообщение на строку, разделитель `\n`, UTF-8; сообщение без встроенных `\n`.
- Невалидный JSON → `-32700`, close.
- Максимум попыток/размер — из конфига.

## 5. Аутентификация (OQ-12)

- Первое сообщение соединения **обязано** быть `rpc.auth` с токеном:
  `{"jsonrpc":"2.0","id":N,"method":"rpc.auth","params":{"token":"…"}}`.
- Сравнение токена — **константное время**; длина токена ≥ 16 (fail-fast при конфиге).
- Успех → `{"result":{"ok":true}}` + сессия помечена authenticated; иначе `-32001` + close.
- `rpc.auth` обрабатывается **на I/O-потоке** (не в реестре).
- Смена токена при `reload` → все сессии инвалидируются (close).

## 6. Очереди, обмен, жизненный цикл

- Две очереди (`Queue<T>`), **отдельный мьютекс на каждую** + condition variable:
  - `inbox` (`I/O→main`): `RpcRequest { handle, sessionId, method, paramsJson, isNotification }`;
  - `outbox` (`main→I/O`): `RpcOut { sessionId, bytes }` (response/notification).
- **Backpressure:** `inbox` полон → отказ `-32004` (генерируется на I/O, отправляется напрямую);
  `outbox` полон → дропаются **нотификации** первыми, ответы не дропаются.
- `requestId`/handle — монотонный `uint32`, **не переиспользуется**; таблица outstanding
  ведётся на главном потоке; `id` (число/строка/null) сопоставляется с handle.
- Notification (`id == null`) → handle не выдаётся (sentinel); `Reply` по нему игнорируется.
- Таймаут `request_timeout` → `-32005`, запись помечается истёкшей; поздний `Reply` отбрасывается;
  повторный `Reply` игнорируется.
- **Дренаж** — в `StartFrame` (`FN_StartFrame_Post`) с бюджетом `drain_budget` за кадр.
- **Shutdown:** wakeup-канал (self-pipe/socketpair) для выхода из `select` + короткий таймаут;
  запрет accept → close всех соединений → join; **идемпотентно** (`OnAmxxDetach`/`Meta_Detach`).

## 7. Логирование

- `Log_*` из I/O-потока **не вызывает AMXX** (`MF_Log*` запрещён вне main): пишет в файл
  и/или кладёт строку в очередь, которую main выводит через `MF_Log`. Секреты не логируются.

## 8. Встроенные методы Этапа 1

- Только минимум: `rpc.ping`, `rpc.version` (и `rpc.auth` — транспортный). Реестр/Pawn — Этап 2.
- `rpc.version` возвращает версию модуля и версию протокола.

## 9. Коды ошибок

См. `docs/02` §4: `-32700`, `-32600`, `-32601`, `-32602`, `-32603`, `-32001`, `-32002`, `-32003`,
`-32004` (busy), `-32005` (timeout).

## 10. Конфиг

Ключи и формат — [`16`](16-config-and-observability.md). Обязательные для Этапа 1: `host`, `port`,
`token`, `max_connections`, `idle_timeout`, `max_message_bytes`, `request_timeout`, `inbox_depth`,
`outbox_depth`, `drain_budget`, `log_level`.

## 11. Верификация

- Сборка win/linux 0 ошибок; модуль грузится.
- Smoke по TCP: `rpc.auth` (верный/неверный токен) → `rpc.ping`/`rpc.version`; ответы корректны.
- Переполнение `inbox` → `-32004`; таймаут → `-32005`; невалидный JSON → `-32700` + close.
- Shutdown без зависания `join`; reload при смене порта/токена.

## 12. Открытые вопросы

OQ-6 (батчи — не поддерживать в Этапе 1), OQ-13 (захват вывода `server.exec` — Этап 2),
OQ-15 (depth/размер guard — §2), OQ-17 (WSAPoll/FD_SETSIZE — §3).

## 13. Ревизия после ревью (резолвы)

**Блокеры**

| # | Проблема | Решение |
|---|---|---|
| B-1 | Запись в закрытый сокет на Linux → `SIGPIPE` убивает HLDS | Игнорировать `SIGPIPE` при старте транспорта (`signal(SIGPIPE, SIG_IGN)`) **и** слать `send(..., MSG_NOSIGNAL)` (Linux). |
| B-2 | Переполнение `outbox` **ответами** не имеет политики (main блокируется → нарушение `NFR-PERF-001`, либо дроп ответов → нарушение политики) | **Per-session bounded outbox** (не глобальный). Переполнение outbox/выходного буфера сессии → **закрыть сессию** (её ответы неактуальны). Main **никогда не блокируется**: при переполнении — помечает сессию на закрытие и продолжает. |
| B-3 | Выходной буфер соединения неограничен (slow consumer DoS) | Cap на per-connection output buffer (`max_session_out_bytes`, дефолт = `max_message_bytes`×`outbox_depth`); превышение → close сессии. |
| B-4 | Если сервер пуст/в гибернации, `StartFrame` может не вызываться → дренаж/таймауты мертвы | **Проверить на тест-сервере до реализации.** Если `StartFrame` не тикает при пустом сервере — предусмотреть альтернативный pump (или задокументировать требование «хотя бы один клиент/бот»; либо использовать движковый таймер). Резолв фиксируется в плане этапа. |

**Major**

| # | Проблема | Решение |
|---|---|---|
| M-1 | Не задан механизм пробуждения I/O-потока при появлении данных в outbox | **Один wakeup-канал** (self-pipe/socketpair) используется и для shutdown, и для сигнала «outbox непуст»: main пишет байт после push; I/O включает его в `select` read-set. |
| M-2 | Владение/блокировка состояния сессий не заданы (гонки, use-after-free) | Сессии — реестр с **монотонным `sessionId` (не переиспользуется)**; состояние сессии пишет только I/O-поток; main адресует ответы по `sessionId` и **дропает**, если сессии нет. `sessionId` в ответе. |
| M-3 | При закрытии соединения неясна судьба pending-запросов | При close сессии: I/O помечает её мёртвой; main при обработке проверяет liveness и не отвечает мёртвой сессии; outstanding-записи сессии снимаются. |
| M-4 | `RpcOut` не различает ответ/нотификацию → «дропать нотификации первыми» нереализуемо | Добавить `bool isNotification` в `RpcOut`. |
| M-5 | Reload: остановка старого транспорта до успешного bind нового → транспорт может лечь | **Pre-bind** нового listen-сокета; только при успехе — останов старого; иначе сохранить прежний и залогировать ошибку. |
| M-6 | `parson` — глубина/переполнение стека не ограничены | Guard **до** парсинга: пред-скан глубины/длины, либо патч/лимит парсера; при превышении — `-32600` + close. |
| M-7 | OQ-4 (JSON-либа) привязан к Этапу 2, но нужен в Этапе 1 | OQ-4 **закрывается в Этапе 1** (`parson`). Обновить roadmap-таблицу. |
| M-8 | `rpc.methods` (FR-RPC-002 «минимум») отложен | Включить `rpc.methods` в Этап 1 (возвращает зарегистрированные методы; в Этапе 1 — только ядро). |
| M-9 | `id` при пере-сериализации может измениться (`1.0`→`1`) | Хранить **сырой токен `id`** из запроса (строка) и эхо-возвращать **дословно**; внутренний handle — монотонный `uint32`. |
| M-10 | Область live-reload не определена (какие ключи применяются на лету) | Live: `log_level`, `idle_timeout`, `request_timeout`, `drain_budget`, `max_connections`. Требуют restart: `host`, `port`, `token`. `inbox_depth`/`outbox_depth` — при следующем старте (или тоже restart). |
| M-11 | OQ-8 (доступ к командам) не закрыт | Дефолт: команды требуют **админ-флага** (`ADMIN_CFG`/`ADMIN_RCON`); `reload` — `ADMIN_RCON`. Зафиксировать в плане. |
| M-12 | Сток логов не определён и не ограничен | I/O пишет в **файл** (просто и не зависит от pump) + опц. строка в очередь в main; очередь логов ограничена, переполнение → дроп с пометкой. Секреты — никогда. |

## 14. Мелкие уточнения (из ревью)

- CRLF: срезать хвостовой `\r` перед парсингом.
- UTF-8: невалидный → `-32700` + close (или пропускать; решить в реализации, не падать).
- Оversize (без `\n` до лимита): просто **close** (не `-32700`).
- Батчи (массив JSON-RPC) — **отвергать** `-32600` (OQ-6 закрыт: не поддерживаем).
- Pre-auth таймаут — **короче** `idle_timeout` (напр. 5 c), чтобы не держать слоты.
- Rate-limit на auth-fail (напр. N попыток/мин/соединение) — опц., loopback.
- `select`/`accept`: обрабатывать `EINTR` (продолжать), `EMFILE` (лог+backoff).
- `max_connections` валидировать ≤ `FD_SETSIZE-1` (clamp/fail-fast).
- `select` fairness: бюджет сообщений/сокет за итерацию.
- `idle_timeout` сбрасывается на любой активности сокета.
- `request_timeout` отсчитывается от постановки в inbox.
- Handle `uint32` — практический wrap несущественен (документируется).
- IPv4-only (host `::1` не поддержан в Этапе 1) — документировать.
- Неизвестные ключи конфига — **warn + ignore** (forward-compat).
- `rpc.methods` спец-кейс для `rpc.auth` (не показывать как обычный метод — либо показывать с пометкой «transport»).
- Версия протокола — константа (`ARP_PROTO_VERSION`) для `rpc.version` (OQ-11 закрыт здесь).
- `SO_REUSEADDR` на Windows → использовать `SO_EXCLUSIVEADDRUSE`.
