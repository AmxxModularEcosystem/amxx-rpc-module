# 10. Системная архитектура (дизайн)

Статус: **черновик (на согласование)**. Область: архитектура модуля-транспорта и его
взаимодействие с внешними инструментами, Pawn-плагинами и движком. Требования — `docs/01`
(AR-001…AR-019, FR-*, NFR-*), решения — `docs/08` §1 (AD-1…AD-8).

## 1. Контекст

Модуль живёт внутри HLDS/ReHLDS, который **однопоточный и не потокобезопасный**: AMXX-ядро
не содержит блокировок вокруг исполнения форвардов, а движок не рассчитан на доступ из
чужих потоков (ресёрч: журнал `0001` §«Решения»). При этом транспорт (TCP-сокет)
естественно требует блокирующего/асинхронного I/O. Отсюда — разделение на I/O-поток и
главный поток как центральное архитектурное решение.

## 2. Диаграмма

```
┌────────────┐   MCP/stdio    ┌──────────────┐   TCP/JSON-RPC   ┌──────────────────────────────┐
│  AI-агент  │ ─────────────► │ MCP-мост      │ ───────────────► │  AmxxRpc (модуль, in-process) │
└────────────┘                │  (в amxb)     │ ◄─────────────── │  ┌────────────┐  ┌──────────┐ │
                              └──────────────┘   responses/push │  │ I/O-поток  │  │ главный   │ │
                                                                │  │ (сокет,    │  │ поток     │ │
                                                                │  │  JSON)     │  │ (AMXX/    │ │
                                                                │  └────┬───────┘  │  движок)  │ │
                                                                │       │ очереди  └────┬──────┘ │
                                                                │       ▼ (mutex)      ▼        │
                                                                │   [I/O→main]  [main→I/O]      │
                                                                └──────────────┬───────────────┘
                                                                               │ natives/forwards
                                                                               ▼
                                                         ┌──────────────────────────────┐
                                                         │ Pawn-плагины (методы/события) │
                                                         └──────────────────────────────┘
```

## 3. Компоненты и ответственность

| Компонент | Ответственность | Поток |
|---|---|---|
| `Config_*` | чтение/reload конфига, fail-fast | главный |
| `Transport_*` | listen/accept, соединения, auth, байты | I/O |
| `Protocol_*` | JSON-RPC кодек, коды ошибок | I/O (парсинг) / главный (сборка ответа) |
| `Queue_*` | мьютекс-очереди `I/O→main`, `main→I/O` | оба |
| `Rpc_*` | реестр методов, диспетчер | главный |
| `Core_*` | встроенные методы (`server.*`, `cvar.*`, `players.*`, `events.*`) | главный |
| `Fake_*` | фейк-игроки, usercmd-think, authid-хук | главный |
| `Bot_*` | опциональный адаптер YAPB | главный |
| `Log_*` | логи без секретов | любой (без AMXX из I/O) |

## 4. Потоки и обмен (ядро дизайна)

Решение (резолв развилки из ревью): **один I/O-поток, неблокирующий мультисокет**
(`select`/`poll`, на Windows — `select`/`WSAPoll`, т.к. `poll` отсутствует). Поток-на-соединение
не берём — он усложняет shutdown/лимиты и не нужен при малом числе клиентов.

- **I/O-поток** (один) обслуживает listen-сокет и все клиентские соединения:
  - `accept` в цикле до `EWOULDBLOCK`; enforce `max_connections`.
  - на каждое соединение — **входной буфер** (фрейминг до `\n`) и **выходной буфер**
    (частичная запись: `send` при `EWOULDBLOCK` — буферизация + регистрация на writability).
  - `rpc.auth` здесь же (не требует AMXX); до аутентификации иные сообщения → ошибка + close.
  - `max_message_bytes` проверяется **по мере накопления** (не после `\n`) — защита от DoS.
  - парсинг JSON → кладёт `RpcRequest` в очередь `I/O→main`; забирает
    `RpcResponse`/`RpcNotification` из `main→I/O` и отправляет.
  - **никогда** не вызывает AMXX/движок; логирование — через потокобезопасный сток (не AMXX).
- **Главный поток** по хуку `StartFrame` (`FN_StartFrame`/`_Post`):
  - дренирует `I/O→main` с **бюджетом на кадр** (`drain_budget`) и **предельной глубиной**
    очереди;
  - для каждого запроса — находит метод, исполняет (C++ или Pawn), формирует ответ;
  - `Fake_*` think — **каждый кадр** `RunPlayerMove` с `msec = frametime` (не throttle по
    фиксированному интервалу; см. `docs/04` §4);
  - собирает события для подписчиков (push);
  - кладёт результаты в `main→I/O`.
- **Блокировки:** отдельный мьютекс на каждую очередь (`Queue`), никаких захватов «одна
  очередь под локом другой»; сигнализация — condition variable. Порядок захватов
  фиксирован и документируется в `design/11`.
- **Backpressure-политика:** ответы (responses) не дропаются; push-нотификации дропаются
  первыми при переполнении `main→I/O`. Переполнение `I/O→main` → отказ `-32004 (busy)`,
  генерируется на I/O-потоке и отправляется напрямую (без очереди в main). Размеры очередей —
  в конфиге (`docs/05`).
- **Shutdown:** I/O-поток спит в `select` с коротким таймаутом **и** wakeup-каналом
  (self-pipe/socketpair/eventfd), чтобы `join` не зависал; сначала запрет accept, затем
  закрытие соединений, затем join; shutdown идемпотентен (`OnAmxxDetach`/`Meta_Detach`).
- **Запросы:** `requestId`/handle монотонны и не переиспользуются; таблица
  outstanding-запросов ведётся на главном потоке; late-reply после таймаута отбрасывается;
  повторный reply игнорируется; при выгрузке плагина его методы снимаются, а его pending-
  запросы завершаются ошибкой (`design/12`).

## 5. Жизненный цикл запроса

1. `rpc.auth` (I/O) — токен → сессия аутентифицирована.
2. Запрос метода (I/O) → парсинг → очередь `I/O→main`.
3. `StartFrame` (главный) → диспетчер → обработчик.
   - builtin: C++ на главном потоке.
   - pawn: публичный колбэк плагина на главном потоке; ответ может быть отложен.
4. Ответ → очередь `main→I/O` → отправка (I/O).
5. Таймаут неответившего запроса → ошибка `-32005` (timeout); `requestId` помечается
   истёкшим, поздний ответ отбрасывается.

## 6. Модель безопасности

- Bind по умолчанию `127.0.0.1`; токен обязателен до любого метода (`AR-007…009`).
- Секреты не логируются; ответы не эхоят токен.
- Лимиты: соединений, размера сообщения, idle, неответивших запросов.

## 7. Ключевые решения (обоснование)

| # | Решение | Обоснование (ресёрч) |
|---|---|---|
| 7.1 | Двухпоточная модель с главным потоком для AMXX/движка | AMXX без блокировок, HLDS однопоточный; эталон — `mysqlx` (worker + `StartFrame`-дренаж). Анти-пример — `webserver_amxx`/`mschnitzer/sockets` (AMXX из чужого потока). |
| 7.2 | `USE_METAMOD` обязателен | нужны `StartFrame`, `GetPlayerAuthId`, `CreateFakeClient` (`AD-7`). |
| 7.3 | Фейки: `pfnCreateFakeClient` + `RunPlayerMove`; свой usercmd-слой | zBot без стабильного API; YAPB без attack; собственный слой даёт точный контроль. |
| 7.4 | Подмена authid — хук `FN_GetPlayerAuthId` | движок отдаёт `"BOT"`; канонический приём — yapb `linkage.cpp`. |
| 7.5 | YAPB — опционально, динамически | `IBotModule` стабилен и версионирован; сохранение опциональности (`AR-016`). |
| 7.6 | Фрейминг — строка-JSON (`\n`) | совместимо с MCP-stdio и byte-pump мостом (`rbash-mcp`); просто. |
| 7.7 | Свой JSON в C++ (`parson`) | Pawn-`json` недоступен из C++; `parson` уже в экосистеме AMXX. TODO-до-этапа: подтвердить и закрыть OQ-4. |
| 7.8 | Один I/O-поток + неблокирующий мультисокет | проще shutdown/лимиты; см. §4. |
| 7.9 | `server.exec` — доверенная граница (RCE по токену) | при токене можно исполнить произвольную серверную команду; документируется, не шифруется (loopback). См. `docs/08` R-4. |
| 7.10 | Плагин **не** может переопределять core-методы | защита `rpc.auth`/`server.exec`/`rpc.*` от подмены плагином; коллизия Pawn = ошибка. |

## 8. Границы (что модуль НЕ делает)

- Не реализует MCP/каталог tools (в `amxb`).
- Не содержит игровой предметной логики (в Pawn-плагинах).
- Не требует YAPB и не падает без него.
- **Не управляет реальными игроками** через `fake.*` (методы отвергают индексы реальных
  игроков) и не превышает лимит числа фейков.
- Не управляет zBot через Orpheu/интерналы ReGameDLL.
- Не управляет реальными игроками через `fake.*` (защита).

## 9. Дорожная карта (этапы)

Детально — [`.omo/plans/0001-strategic-roadmap.md`](../../.omo/plans/0001-strategic-roadmap.md).
Кратко:

0. **Bootstrap** — каркас репо, SDK-вендоринг, CMake, CI, загружаемый модуль-пустышка.
1. **Транспорт** — TCP, фрейминг, auth, I/O-поток + очередь + StartFrame-дренаж, конфиг.
2. **RPC/Pawn** — реестр, ядро методов, нативы регистрации.
3. **Фейк-игроки** — движковый слой, authid, usercmd-think, `fake.*`.
4. **Боты (опц.)** — YAPB-адаптер, деградация.
5. **Hardening** — бандл amxb, пример, e2e, документация.

Каждый этап — по циклу `feature-delivery` (дизайн → ревью → план → ревью → реализация → запись).
